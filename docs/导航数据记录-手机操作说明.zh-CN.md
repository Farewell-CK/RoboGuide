# 导航数据记录：手机操作说明

适用目标版本：`1.4-swinl-npu-384-v16-archive`。功能集成在原来的 D455f、VINS、Swin-L 384×288 导航源码中。本轮另提供独立包名的测试构建，以便在签名不同的手机上保留既有应用。

## 测试包和既有应用怎么区分

| 构建或应用 | 包名 | 手机上的用途 |
|---|---|---|
| 原应用 | `com.seaway.guideassistant` | 保留原应用 |
| 既有Swin-L版本 | `com.seaway.guideassistant.swinl` | 保留已安装的v15等版本；同包更新需要签名一致 |
| v16独立测试构建 | `com.seaway.guideassistant.swinl.archive` | 名称为 **导航助手·数据测试**，验证新归档功能 |

v16测试包使用同一套导航及归档代码，只通过构建参数改变应用标识和名称。它不是把上传做成手机外部工具。测试包有独立的数据目录和设置，需要在包内重新配置平台；不会自动读取其他包的历史档案。

Mac本机debug签名与手机既有Windows构建签名不同时，不能直接覆盖既有Swin-L应用。独立测试包允许并存，不需要卸载原应用或v15。已在 Redmi K70 Ultra 上安装并核对 v16 测试包，完成真实 D455f 录制、千问视觉调用归档、本地 ZIP 导出和上传到本机参考平台的验证。

从工程 `source/` 目录构建测试包：

```bash
source ../.tools/env.sh
./gradlew :app:assembleDebug -PswinlFast=true -ParchiveTest=true --no-daemon
```

产物位于 `app/build/outputs/apk/debug/`。本轮构建文件为 [archive_v1.4-swinl-npu-384-v16-archive_20261110110112_debug.apk](../app/build/outputs/apk/debug/archive_v1.4-swinl-npu-384-v16-archive_20261110110112_debug.apk)。不传 `-ParchiveTest=true` 时，目标包名仍为 `com.seaway.guideassistant.swinl`。

## 在哪里操作

打开本轮测试构建时，选择 **导航助手·数据测试**，进入导航页面，点击 **导航数据记录**。手机端提供本地记录列表、大小与状态、导出ZIP、平台地址配置、自动上传和“上传 / 继续上传”。平台网页负责查看手机上传后的数据。

## 随导航记录，不再单独开关录制

1. 不配置平台地址，或保持自动上传关闭。
2. 输入目的地，点击 **开始导航**。软件在发起路线规划前创建本次档案，因此规划、开始请求、起终点及随后发生的相机/VINS初始化都在记录范围内。点击目的地候选会按原有流程直接规划并开始导航，也从这次点击开始记录。
3. 导航结束后点击原来的 **结束导航**。多阶段任务在最后阶段结束或取消任务时封存整份档案；到达目的地的提示本身不会自动推进阶段或停止记录。等待规划时原来的开始按钮显示 **取消导航**，可用它取消未完成的路线请求并结束记录。
4. 进入 **导航数据记录**，查看该次导航。点击 **导出ZIP**，在系统文件选择器中选保存位置。

已移除独立的“开始数据记录 / 结束数据记录”按钮。录制期间入口显示 **导航数据记录（正在记录）**；录制中的记录不能导出ZIP，已写完的文件可以先上传。单次导航若无法开始或规划失败，会保存失败原因并结束这次记录；多阶段任务的阶段失败会保留在同一档案中，便于重试。

单纯打开软件、编辑目的地或调用千问解析指令，不会单独创建导航档案。智能体下发的多阶段计划在实际开始阶段时建档：室外阶段由开始导航触发，室内阶段在实际下发导航指令时触发。解析结果和原始导航指令会写入随后开始的任务档案；导航期间发生的千问调用写入已有档案。

开始前已完成的相机/VINS初始化不会伪造为开始后的过程，但软件会把当时缓存的运行配置连同观测时间写入档案。开始后的初始化状态和输出继续记录。相机、定位、VINS或模型尚未就绪时，不会虚构对应结果；是否实际生成数据以文件清单和采集摘要为准。

结束时先停止接收新的采集输入，并写完已进入队列的视频、深度、传感器和地图文件。结束时还没有返回的语义推理或千问请求会标注为未完成，不把它们当作已有结果。异常退出后，下次启动恢复已写入的文件并标为异常中断。

## 起点和终点在哪里

本次档案的 `navigation.requested` 事件保留起点栏显示文字和终点输入。当前起点栏固定为 **我的位置**，实际规划采用手机定位；可用时保存WGS84经纬度、来源、精度、定位时间及在开始请求时的年龄。没有定位时明确标为不可用。目的地候选和高德解析后的终点使用GCJ02坐标，并保留路线、距离、预计时间和步骤。

## 实验标注和结果

在 **导航数据记录** 页，对一条记录点击 **实验标注 / 结果**，可填写实验编号、场景备注、人工到达确认、人工接管确认、失败原因、补充说明及发生于导航开始后多少秒。所有项都可留空或保持 **未确认**；“未确认”表示未知，不能当成没有到达或没有接管。

导航过程中可以填写，结束后也可以补填。发生时间若由你输入，会保留为人工填写；录制时留空使用保存时刻，结束后留空则保持未知。录入时间与事件发生时间分别保存。

每次保存都会追加一个版本并保留历史。已经导出的ZIP需要重新导出，已经上传的记录需要重新上传才能带上新标注。封存时的 `capture-summary.json` 可能早于后补标注；查看结果应以清单中 `artifacts/experiment_annotation/` 里最大 `revision` 的标注为准，不用旧摘要覆盖新标注。

## 连接本机测试平台

电脑在 `source/platform/` 启动：

```bash
python3 archive_server.py --data-dir ./archive-data --port 8765
```

电脑浏览器打开 `http://127.0.0.1:8765/`。手机通过USB或无线调试连上ADB后，在电脑建立反向端口转发：

```bash
adb -s 手机IP:无线调试端口 reverse tcp:8765 tcp:8765
```

手机 **导航数据记录** 页填写：

- 平台地址：`http://127.0.0.1:8765`
- 访问令牌：本机服务未配置令牌时留空；已配置则填写同一个令牌。

点击 **保存平台配置**。这个HTTP地址仅用于debug联调，通过ADB转发到电脑；ADB断开后通常需要重建转发。正式部署填写HTTPS地址。

如果已经保存访问令牌，输入框留空表示保留它；要删除则勾选 **清除已保存的访问令牌** 后保存配置。

## 删除不需要的本机记录

在 **导航数据记录** 页找到对应时间的记录，点击下面的 **删除本机记录**。核对弹窗中的时间和大小，再点击 **删除**。确认后会删除这一条记录的应用内部数据及内部缓存ZIP，释放手机空间；其他记录保留。

正在记录、上传或导出时不能删除，请等待完成或先结束记录。你已经另存到“下载”等文件夹的ZIP、电脑平台上的副本都不会随本机记录删除；另存的ZIP可以在手机文件管理中单独删除。删除应用内部记录后无法恢复，需要保留的数据应先导出。

## 上传方式

- **手动上传**：对一份记录点击 **上传 / 继续上传**；失败后可再次点击，从平台确认的进度继续。
- **自动上传**：开启 **自动上传（导航中上传已保存片段，失败后重试）**。配置了平台后约每15秒检查一次，上传已完成的视频片段、数据文件和事件段；正在写入的片段暂不上传。
- 导航结束后会提交最终文件清单，平台核对齐全且校验一致后，显示最终保存完成。

上传成功不会自动删除手机档案。上传或导出时尽量保留足够手机空间。

## 录下了什么

| 内容 | 当前录制方式 |
|---|---|
| 彩色视频 | 目标640×480、15帧/秒、H.264、1Mbps，约30秒一段，不录音频 |
| 每次实际语义推理的输入 | 一张配对JPEG关键帧、原始Z16深度、对齐Z16深度；深度用gzip无损压缩 |
| Swin-L结果 | 384×288类别标签图、逐像素置信度和耗时 |
| 语义点云 | 每10秒选一份新结果，包含地面、道路和障碍物 |
| 地图与规划 | 局部代价图、路径、转向、受阻和重规划；完整`.navmap`检查点、其无损字节差分及结束包 |
| 过程事件 | 任务、定位/方向、IMU、VINS、距离摘要、提示/播报、操作、模型请求/响应和是否被使用、性能与异常 |
| 完整运行配置 | 构建编号/源码与原生库身份、手机和Android版本、相机固件/实际流、相机与IMU标定、曝光采样、定位及规划关键参数；不可用值明确标注 |
| 随包说明与采集摘要 | `README.zh-CN.md`、`data-dictionary.json`、`capture-summary.json`，说明格式/单位/坐标系、实际文件数、模块就绪状态、缺失或失败原因 |
| 实验标注与结果 | 默认以会话编号作为实验编号；可选场景备注、人工到达/接管确认、失败原因及发生时间，保留标注版本 |

连续原始RGB帧和相机30帧/秒的连续深度不归档；它们仍正常供导航计算使用。保存的推理采集组共用编号，便于在平台对照彩色画面、深度和语义结果。

拿到新录制的ZIP后，先读 `README.zh-CN.md` 和 `capture-summary.json`，再按 `data-dictionary.json` 解释数据。文件数为0不自动表示丢失：例如VINS未就绪时可能根本没有生成语义结果或地图；摘要会结合已观测事件给出状态，原因不能确定时保留未知。

完整运行配置保存在 `artifacts/runtime_configuration/`。开始后重新初始化或新取得的配置、曝光信息还会写入 `runtime.configuration` 过程事件；请结合每项观测时间读取，未支持或未观测的字段不当作有效值。

## 怎么看状态

- **正在记录**：导航尚未封存。
- **已结束**：本地录制已封存，不等于已经上传。
- **已结束，存在缺失**：有队列、编码、写入、地图导出等问题；查看相关事件。
- **异常中断后恢复**：上次进程未正常结束，重新打开后恢复了已写入文件。
- **已上传当前片段，导航仍在记录**：现有封存文件已经上传，还会继续产生文件。
- **平台已保存并校验**：最终清单里的现有文件都被平台保存并校验。

采集完整性和平台保存状态分开：一份录制有缺失的档案，也可能把现有文件全部成功上传。不要只根据“平台已保存”判断当时没有丢帧。

## 平台查看

在电脑网页打开一份记录：

1. 查看采集状态、文件大小和接收进度。
2. 对MP4点击 **播放**，拖动片段时间；时间线会查询附近的过程事件。
3. 对JPEG、深度、语义图或栅格点击 **预览**；深度预览可查看像素原始值及米制距离。
4. 下载清单或文件，用于后续分析。

平台的点云预览是俯视抽样显示；完整已记录点保留在下载文件中。OctoMap完整包为`.navmap`，里面有`occupancy.ot`和`semantics.bin`。普通`.ot`没有保存全部语义字段，因此分析完整地图时应保留整个包。当前地图会裁掉较远区域，结束包不自动等于整段路程，需要沿途的检查点和差分。

在电脑工程`source/`目录，可以用下面的工具核对导出档案和恢复地图：

```bash
python3 tools/inspect_navigation_archive.py exported.zip --json
python3 tools/inspect_navigation_archive.py exported.zip --reconstruct-maps ./restored-maps
python3 tools/inspect_navigation_archive.py --map-info "./restored-maps/<恢复出的文件路径>.navmap" --json
```

替换为实际路径；恢复目录须是新建或空目录。工具恢复的是完整`.navmap`包，并核对校验值；它不会把缺失的地图版本补造出来。

## 验证范围

2026-11-09 的真实 D455f 测试已验证硬件 H.264 编码、平台视频加载、推理 RGB/原始深度/对齐深度配对、完整地图导出与历史恢复、手机 ZIP 导出、手机上传及平台逐文件校验。千问视觉测试取得93次HTTP 200响应，并记录图片、原始响应、结果是否采用和Token用量。协议测试覆盖分块中断、重启续传及录制中追加；长时间实地导航、手机无线断开后恢复和新旧版本严格性能对照尚需后续验收。完整树导出在运行时分别核对占用树拓扑/占用值，以及语义sidecar与原树各字段，并检查原生库身份；若适配失败会记录错误，不把局部叶子快照或普通.ot冒充完整语义地图。
