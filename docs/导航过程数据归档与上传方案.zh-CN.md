# 导航过程数据归档与上传方案及实现说明（v16）

更新日期：2026-11-10。依据：老师要求“开发上传所有过程数据的接口，并完成平台保存数据”，以及本次聊天确认的采集范围。当前目标版本为 `1.4-swinl-npu-384-v16-archive`。本文保留已确认的数据范围，并按当前源码更新接口和存储说明；硬件与完整导航验收以实测报告为准。

## 1. 建设目标与范围

以一次导航任务为单位，在手机生成可校验的过程档案，支持本地保存、导出、上传，以及平台持久保存、查询、回放和下载。室内外阶段共用任务编号，能够沿时间线追查“当时看到了什么、算法输出了什么、实际发出了什么提示、为何停止或等待”。

“所有过程数据”在本方案中指下面确认的业务输入、算法输出、地图、交互、状态和诊断数据。采样策略会写入清单：视频初步15 FPS，语义点云每10秒选一份，其余按对应事件或实际结果记录。它不是所有原始传感器帧、模型全部中间张量或内部优化矩阵的无损备份。

不归档连续原始RGB帧，也不按相机30 FPS全量保存深度；仅保存每次真正执行语义推理所对应的一组原始Z16深度和对齐深度。暂不录制音频。彩色画面通过压缩视频、云端模型实际使用的JPEG和每次推理对应的JPEG关键帧保留。Swin-L输入/输出仍为384×288，相机采集保持640×480、30 FPS。

其他未选中的深度帧仍供现有导航算法正常使用，处理完后释放。档案支持检查选定推理的深度、分割及建图关系；由于未保存连续原始RGB-D帧，仍不能承诺重新运行完整VINS并逐帧复现全部导航结果。

## 3. 视频方案

- 来源：复用D455当前彩色流。录像不改变VINS使用的相机帧率或模型分辨率。
- 参数：640×480、15 FPS、H.264、MP4、目标1 Mbps。目标手机已验证硬件编码可用，优化后短测平均14.999 FPS；严格同条件导航性能对照仍需补充，实际参数写入档案。
- 压缩含义：视频从30 FPS采样到15 FPS，并使用有损视频编码；保持640×480尺寸。不能将压缩视频当作原始逐帧RGB数据。
- 分段：约30秒一个可独立播放的片段，在关键帧边界完成封装；最后不足30秒也封存。异常退出未完成的片段标为损坏或未封存，恢复时尽可能修复，不标记正常。
- 时间：保存原始采集时间/单调时钟与视频PTS映射，录制暂停和丢帧保留时间间隙，不将片段直接拼接成“从未中断”。
- 展示：干净视频与算法结果分别保存，平台回放时可叠加时间、提示和地图，保留原始画面的可见性。
- 体积：1 Mbps约7.5 MB/分钟、450 MB/小时，加少量封装开销；实际由编码器输出决定，不承诺固定值。

## 4. 时间线与可追溯关系

每份档案有session_id，每次启动或时钟/定位重置有独立编号。档案清单包含schema_version；过程事件包含session_id、type、wall_time_ms、elapsed_time_ns和data，传感器另保留原始采集时间和时间域。区分WGS84/GCJ02、相机系、IMU系、VINS世界系及局部地图系，保留单位、矩阵排列和四元数顺序。

当前以采集帧号、inference_id、generation、地图sequence、云端request_id及文件相对路径关联结果；视频元数据保存帧号、采集时间和PTS对应。采集位姿与投影位姿分别存，VINS重启后不能把不同generation的点云或地图直接拼在一起。

目标查询示例：回放某秒的视频时，能查到对应分割、大模型描述、距离摘要、地图、规划和实际提示；一条停止提示能追到其引用的地图、定位新鲜度和阻塞/等待原因。

起点显示文字与实际规划起点分开记录。当前界面起点栏固定为“我的位置”，实际起点来自Android手机定位，坐标系为WGS84；高德目的地候选、解析终点及路线为GCJ02。手机定位保留精度、来源、定位时刻和开始请求时的年龄，缺少定位时标明不可用，不从文字推断坐标。`navigation.requested` 保存用户开始请求，成功后 `global_route` 和开始定位事件补上实际路线/起点信息。

## 5. OctoMap的两类“完整”

### 5.1 当前内存中的完整树

原有nativeExportLeafs只导出局部占据叶子。进一步核对发现，现有原生库的普通`.ot`序列化会遗漏语义置信度、语义显示标记，以及原始RGB和语义RGB的分别保存。因此仅做“.ot写出—读回—再次写出字节相等”，不能证明所有语义字段保留完整。

v16完整快照改为确定性ZIP容器 **`.navmap`**，包含且只包含：

- `occupancy.ot`：兼容OctoMap的占用/几何树。读回时与原树核对拓扑、占用值、树深度、分辨率及节点/叶子数；不依赖它恢复完整语义。
- `semantics.bin`：`NSEM0001`格式的权威完整节点状态，保存每个节点的深度/路径/子节点掩码、原始占用float位值、原始RGB、语义RGB、置信度float位值和语义显示标记。写出后逐字段读回，与未修改的原树比对。

容器条目采用ZIP STORED及固定时间，NDT1差分作用于整个`.navmap`字节。sidecar头为96字节小端格式，携带版本、分辨率、节点数及库身份；每节点25字节，覆盖全树节点而非仅叶子。

完整节点读取适配器依赖当前原生二进制布局，因此Java先校验APK或解压目录中`libelabrador_native.so`的SHA-256，原生端再校验实际已加载库的GNU build-id。当前指纹为SHA-256 `cf6006b3dd366788a88febe994302be77d431c62d501feabeaa58a349261ed61`、build-id `7bf75c29a7ba8e49050444dbb36867b0bc487a0d`；不匹配即禁用该适配并记录错误，不能对未知版本套用节点偏移。

此格式已在目标手机运行验证，85个沿途版本和1份结束快照的完整语义包已恢复并解析通过。ABI身份不支持、原始节点与sidecar字段比对失败、占用树读回不一致时标记采集错误，不能据构建或解析测试通过认定真机完整树导出已验收。

局部叶子检查点和差分另外保留，范围明确为`local_occupied_export`。其中scope_exit只表示不再出现在局部导出中，可能离开了窗口，不等于地图中障碍物已删除或变为空闲；它不替代完整`.navmap`。

### 5.2 整段路程的地图历史

当前地图有约10米裁剪，结束快照不会包含早已裁掉的远处区域。v16按generation保存首个完整检查点、此后各版本的无损文件字节差分，每第10个成功快照再保存完整检查点；结束时登记最后一份成功验证的完整快照。

完整树差分为gzip容器中的`NDT1`格式，包含目标`.navmap`文件长度及需替换的字节区间，元数据记录base_sha256和目标sha256。它保留占用树和完整语义sidecar整个包的精确变化，能从检查点按顺序恢复各次`.navmap`；不是直接描述“哪个体素新增、修改或删除”的业务消息。恢复须校验基文件及目标文件哈希，不能跨generation套用；中间丢失时等待后续完整检查点，不虚构缺失版本。

为归档保留历史不改变原导航地图的裁剪和规划规则。历史回放保存随时间变化的地图，不把所有历史障碍叠成一直存在的静态图。

## 6. 手机端实现

录制器直接从采集、模型响应、语义结果、建图、规划和播报等实际生产位置接入，避免只抓UI截图。用户点击原有“开始导航”时，先建立档案，再发起规划；选择目的地候选直接开始规划时同样先建档。规划、开始请求、起终点及后续初始化均在这个窗口内。单次导航开始失败也保存失败原因并封存；多阶段任务在同一档案记录阶段失败与重试。

千问解析指令不会单独创建档案。多阶段计划在真正开始阶段时建档：室外从开始导航动作触发，室内从实际下发导航指令触发；将已解析的指令/结果写入任务开头，室内/室外阶段共用会话。点击结束导航、取消任务或最后阶段结束时封存；到达提示本身不会停止记录。等待规划期间原开始按钮变为“取消导航”，取消后使原请求generation失效，防止晚到的路线回调重新启动导航。

正常页面重建不拆分一份档案；实际关闭应用时结束，进程异常退出后下次启动恢复未结束档案并标为异常中断。结束先停止新增输入并写完已入队视频、推理输入深度、IMU/特征及最后成功地图；结束时仍未返回的语义推理/云请求写入未完成标记，不虚构结果。

事件中完整的artifact元数据关联文件及采集信息，清单文件条目保存大小、SHA-256、类型与简要元数据。ZIP导出包含清单及其列出的已封存文件，不包含认证配置或上传进度。

`runtime_configuration` 保存建档时的应用/手机/构建身份和实际导航参数。相机/VINS等已经初始化时保存带观测时间的缓存配置；开始后新观测或重新初始化的配置写入 `runtime.configuration` 事件，曝光元数据按实际可取得值采样。不支持或本进程未观测的字段保留 `available=false` 及原因，不能将默认目标值冒充实际采集值。

封存时生成 `README.zh-CN.md`、`capture-summary.json` 和 `data-dictionary.json`，并列入有哈希的文件清单。摘要统计已持久保存的类型/文件/事件及体积，列出模块就绪证据、失败/缺失事件和结束时未完成的处理。没有地图文件可能是VINS未就绪、没有语义结果或导出失败，摘要依据可见证据区分；不能确定时明确保持未知，不补造数据。

人工标注通过“实验标注 / 结果”填写。默认实验编号为session_id；到达与接管默认 `unconfirmed`，不等同于否。发生时间 `relative_seconds` 与实际录入时间分别保存，标明人工填写、录制时采集或未指定。每次保存追加 `artifacts/experiment_annotation/revision-*.json` 并保留历史，当前人工说明以清单中最大revision为准。封存后标注可能晚于 `capture-summary.json`，不能用旧摘要覆盖新版本；补标注后需重新导出ZIP或重新上传。

二进制文件明确大小端、类型、形状、字段顺序、单位；标签用无损uint8保存65类，置信度初版保留float32。文本和适用的二进制可使用无损压缩，避免用超大JSON数组/Base64归档点云或视频。

当前深度用gzip压缩原始Z16字节，保留16位值、行stride和深度单位，不使用JPEG或着色后的深度预览图替代。原始与对齐深度必须在采集/对齐环节绑定到推理输入，在真正执行推理时归档；推理结束后再读取最新深度会错位。每对保存inference_id、RGB及depth帧号、配对时间差、原始与映射时间、宽高/stride/units、内外参及对齐版本。被队列替换的未执行输入不归档；已执行但失败的输入可用于排错，标明失败状态。录像或云端图片不保证恰好覆盖该RGB帧，已确认额外保存同次推理的一张压缩RGB关键帧，作为彩色—深度—语义结果的对应证据。

生产线程仅投递有界快照，磁盘写入、视频编码和网络在独立后台工作。内存队列有上限；过载优先维持导航，缺失记录进入清单。磁盘空间不足时提示用户并停止或降级录制，具体策略明确记录，不能默默删除历史档案或谎称完整。上传按文件流式读取。

原导航页保留“导航数据记录”入口，提供记录列表、大小、本地状态、丢记录提示、上传状态与错误、ZIP导出、实验标注、删除、平台配置、自动/手动上传及重试；未配置平台时正常本地录制。独立“开始数据记录 / 结束数据记录”按钮已移除，由导航开始、结束和取消统一控制，录制时入口显示“正在记录”。为与既有签名不同的v15并存，`-ParchiveTest=true`构建使用`com.seaway.guideassistant.swinl.archive`及名称“导航助手·数据测试”，与默认包共用源码。详见[手机操作说明](导航数据记录-手机操作说明.zh-CN.md)。

## 7. 当前上传接口 v1

平台地址可配置，默认使用HTTPS；debug只允许指定的本机/模拟器HTTP地址用于联调。支持仅本地、自动上传和手动继续上传。自动上传开启且已配置平台时约每15秒检查一次，上传已经封存的文件；正在写入的MP4不上传。

会话用扩展清单登记文件，不设置单独的descriptor接口。录制中提交state=recording的清单快照，后续可以增加文件，但旧条目的路径、大小、哈希及描述保持不变。导航结束提交最终清单，再请求整份档案确认。过程事件段按大小或上传flush封存，只有列入清单的完成文件进入上传。

封存后仅允许追加经过校验的 `experiment_annotation` 标注版本，不允许修改或删除既有采集文件，也不重写原封存报告。再次上传时平台接收追加文件并重新核对整份清单；此前导出的ZIP不会自动更新。

| 实际接口 | 功能 |
|---|---|
| PUT /api/v1/sessions/{id} | 创建会话、扩展recording清单，或提交最终清单；旧文件不可修改/删除 |
| PUT /api/v1/sessions/{id}/files/{相对路径}?offset=...&sha256=... | 上传二进制分块，单块不超过4 MiB |
| GET /api/v1/sessions/{id}/upload-status | 查询平台已持久保存字节偏移及每个文件状态 |
| POST /api/v1/sessions/{id}/complete | 请求体{}；必须先提交最终清单，全部文件校验通过才返回complete |
| GET /api/v1/sessions | 最近1000份导航记录 |
| GET /api/v1/sessions/{id} | 当前清单及上传状态 |
| GET /api/v1/sessions/{id}/manifest | 下载当前或最终清单 |
| GET /api/v1/sessions/{id}/events | 最近事件；可用offset/limit分页及since_ms/until_ms按Android单调时间毫秒过滤 |
| GET /api/v1/sessions/{id}/files/{相对路径} | 鉴权下载；支持单个Range区间，视频拖动时可请求部分字节 |

同一清单或相同文件分块可以重复发送，内容冲突拒绝覆盖。重连以服务端确认进度为准。录制中即使当前文件传完也只显示receiving，最终清单校验通过后才显示平台保存完成。平台与手机采集状态相互独立，详见[平台接口文档](../platform/README.zh-CN.md)。

## 8. 平台保存与使用

当前参考平台由Python标准库HTTP API、SQLite会话索引、磁盘文件存储和网页组成；事件按JSONL文件查询。部署时可按既有平台环境适配数据库和文件系统/对象存储。大视频、点云不直接塞入数据库字段。

文件写入临时位置并记录进度，完成后校验大小和SHA-256，再原子转为正式文件；整份档案验证完成后返回明确确认。服务重启后数据和上传偏移仍存在。上传成功后本地默认保留，清理由用户明确操作，平台备份同时覆盖数据库与文件。

当前网页提供：

1. 导航记录列表：任务编号、开始时间、文件数、大小、采集与保存状态，详情清单包含版本及其他元数据。
2. 详情：文件清单、接收偏移、当前状态、配置和错误事件；覆盖率及缺失区间的专门汇总界面可继续扩展。
3. 时间线：播放已上传视频片段并按对应时刻查询附近事件，另可查看最近事件或通过API分页查询。
4. 结果查看：JPEG、语义标签/置信度、局部栅格、gzip深度二维预览和点云俯视抽样预览；完整三维OctoMap交互浏览尚不在当前页面中。
5. 文件与校验清单下载，使平台外也能使用档案；手机另有整份ZIP导出。

分别显示手机采集状态（完整/有缺失/异常中断）和平台保存状态（本地/待上传/上传中/失败/已校验保存）。采集有缺失的档案也能上传成功，两种状态必须独立。

## 9. 体积与性能预算

以下使用十进制MB，仅为初步预算，地图/图片实际体积需实测：

| 数据 | 预算口径 |
|---|---|
| 视频 | 约7.5 MB/分钟，1 Mbps目标码率 |
| 标签及置信度 | 110592像素×(1字节标签+4字节置信度)，按18～20次结果/分钟约10～11 MB/分钟，未做无损压缩 |
| 推理对应的两种深度 | 640×480×2字节×两种×18～20次，约22.1～24.6 MB/分钟，未做无损压缩；实际由执行次数和stride决定 |
| 10秒一次语义点云 | 最多110592点×20字节×6次，约13.3 MB/分钟上限；有效点少时更小 |
| 云端JPEG | 只保存实际请求图片并去重，按现场画面和调用次数实测，不把Base64字符串重复落盘 |
| IMU/VINS/栅格/事件 | 采用批量二进制与结构化文本，分别统计 |
| OctoMap | 由地图节点与变化规模决定，完整树导出验证后测量，不给未经验证的固定值 |

视频+标签/置信度+点云三项约31～32 MB/分钟；加入按推理选帧保存的两种深度后，这几项合计约53～57 MB/分钟（未计地图和JPEG等、未做无损压缩）。这些是累计文件大小，不是常驻运行内存；深度保存量随实际执行推理次数变化。

运行内存与累计文件大小分开测量。对比当前384×288 NPU基线，记录开启归档前后推理耗时、地图间隔、VINS跟踪、帧丢失、内存峰值、温度和续航；性能门限根据同条件实测确定，不能只凭硬件编码推断无影响。

## 11. 验收标准

- 正常导航结束后，本地具有清单、可播放视频和范围内各类记录；抽查时间、帧和提示能够关联。
- 点击开始导航后、规划发起前已建档；起点显示文字/定位和终点输入/解析坐标可追查，开始失败保留原因，等待规划可取消，迟到回调不能重启记录。
- 新档案包含完整运行配置、随包说明/字典和采集摘要；未知配置或未就绪模块不误报为正常，文件为0时不直接推断丢失原因。
- 人工到达/接管确认与算法事件分开，支持未确认和结束后追加，时间来源及revision保留；后补标注不会改写既有观测文件。
- 点云10秒采样包括地面，不重复保存同一观测；模型结果按384×288实际输出记录，不将UI重绘计为新图。
- 深度只保存实际推理输入对应的原始/对齐帧，核对帧号、时间配对和标定；无损读回后16位值一致，不以推理完成时最新帧替换。
- 云端请求/响应/拒绝原因可追查，凭据不在导出的文件中。
- 完整`.navmap`中，occupancy.ot读回核对拓扑/占用，semantics.bin核对原树全部已定义语义字段；普通.ot单独不视为完整语义快照。历史裁剪、局部导出、不同generation均明确区分，原生身份不匹配时拒绝适配。
- 断网/超时/重复请求/客户端重启/平台重启后可恢复上传，文件无重复、无内容冲突；失败可见。
- 丢帧、相机断开、后台切换、磁盘不足和异常退出形成缺失区间；不能把有缺失档案标为完整采集。
- 平台确认保存后重启服务，重新查询、下载所有文件，大小和SHA-256与本地一致；视频可拖动播放。
- 真机开启录制和上传后完成同条件导航性能对照，报告实际峰值与影响，不能用构建成功代替性能验收。

## 13. 离线检查与地图恢复

解析器接受手机导出的ZIP或会话目录，从工程`source/`目录执行：

```bash
python3 tools/inspect_navigation_archive.py exported.zip --json
python3 tools/inspect_navigation_archive.py exported.zip --reconstruct-maps ./restored-maps
python3 tools/inspect_navigation_archive.py exported.zip --map-info "artifacts/octomap_full_checkpoint/<清单中的编号>.navmap" --json
python3 tools/inspect_navigation_archive.py --map-info "./restored-maps/<会话>/generation-<编号>/<恢复出的文件>.navmap" --json
```

上述尖括号部分应替换为清单或恢复输出的实际路径。`--reconstruct-maps`要求目标目录为新建或空目录，按generation/sequence应用NDT1并核对每个恢复包的SHA-256。恢复结果是包含`occupancy.ot`和`semantics.bin`的`.navmap`，不是单独的`.ot`。工具兼容旧格式`.ot`字节链，但旧格式不具备本版完整语义保证。

`--map-info`检查包内唯一成员、ZIP CRC、NSEM0001头、记录长度、节点路径/拓扑、节点/叶子计数及字段范围，显示原生库指纹和语义置信度等摘要。这是文件格式检查，不代替从手机原始内存逐字段比对的运行时验证。
