# ADR-0231 本机具身操作系统与设备的两类接入

状态为首轮部署实现。2026-11-04 已提供显式部署目录中的 `task.delegate@v1`、
Robonix 侧任务协议模块和 Node 配置，并完成狗2的一次原地站立闭环。
公共默认目录的推广、两类参与者协作和运动取消仍按后续验收推进。
实际身份、原始结果和早期失败见 [验收记录](../development/acceptance/2026-11-04-robonix-task-delegation.md)。

## 问题与目标

RoboGuide 的目标是协调异构具身体、计算节点和交互设备。真实机器狗接入用于检验
RG 的任务表达、参与者选择、资源协调、执行跟踪和故障恢复。站立是首个小范围用例，
后续验收还要覆盖多个参与者协作。

狗2运行的 Robonix 已有本机任务入口、Pilot、Executor 和底盘原语。如果每次使用新原语
都要求在 RG 建立一个全局操作及独立工作流，会把本机任务分解带入全局接入配置。
现有 ADR-0036 已允许一个完整 Local EAIOS 能力封装多个内部步骤，本提案延续该边界。

## 两类接入共用 RG 执行协议

| 接入形态 | 本机责任 | RG 侧责任 |
| --- | --- | --- |
| 本机具身操作系统接入 | 接收受支持的目标，决定是否受理，规划与执行本机步骤，确认本机结果，处理取消及即时安全 | 选择参与者，承诺资源，通过统一任务入口委派目标，保存任务关联，消费进度与结果，协调其他参与者 |
| 设备接入 | 由设备已有 runtime 或本地执行适配层调用 SDK、驱动或控制器，实现所声明操作及状态、取消和本地保护 | 按声明的能力调度设备，将其操作纳入相同的 Mission、Commit、Bind 与恢复流程 |

本机具身操作系统接入可复用配置化 Node Service。兼容层仅在协议或状态语义存在实际
差异时承担转换。Node Service 使用通用驱动，本机任务规划与运动逻辑由本地系统实现。

设备接入可以部署在设备计算单元或邻近网关上。网关承载的 Node、Host、LocalSystem
与物理设备分别保留身份。同一 Node 可以承载多个有明确 owner 的能力。
仅有摄像头的设备可以先参与采图任务。新增导航或抓取能力需要相应的本地执行实现。

接入形态表达本地系统承担任务的方式。两类参与者共用现有的注册、资源、执行身份、
状态和恢复机制，逻辑模块可以由同一个常驻进程承载。

## 能力目录与任务委派

Canonical Capability Catalog 规定公共能力和操作的含义及参数。节点注册提供当前
能力、操作支持和资源证据。Node 的私有 Operation Binding 负责具体协议转换。

完整任务的本机步骤由 Local EAIOS 管理。只有 RG 需要独立选择执行者、承诺资源、
协调或恢复某个步骤时，该步骤才形成全局 Task/Role 边界。

拟增加显式、可选择启用的统一任务委派合同。一个绑定能够传递不同的本机目标，例如
在同一姿态任务范围内请求起身或趴下。绑定对应的任务范围、资源占用和本机结果含义
由部署明确声明；本机系统保留逐任务受理或拒绝的职责。

对于用户指定狗2的请求，应通过现有实体与 Actor 绑定机制落实目标身份，并继续经过
Control 的资源检查与 Commit。对于“选择一台机器人巡检”的请求，RG 还需要可比较的
任务能力声明、相关世界信息和当前部署证据。统一入口的可达性只提供通信事实。

目录扩展须明确操作语义、可接受的参数、所需能力和任务结果依据。现有目录外操作
继续需要显式的语义定义。任务范围与本机准入策略必须对应，纯文本目标承载任务内容，
实际执行权限由本机已安装的策略和已授予资源约束。

## 委派任务的执行责任

- RG 保存原任务、attempt、目标与约束，以及它与本机任务身份的关联。
- Local EAIOS 明确报告受理、执行中及本机终态，拒绝时提供可归属到原任务的原因。
- 本机结果的适配规则由对应接口的实际语义决定。流结束、最终文字或单个工具返回值
  分别保留原含义；任务完成需要本机任务级结果。RG Orchestration 根据声明的
  satisfaction basis 决定全局 Task 是否满足。
- 本机姿态、导航收敛和硬件状态由 Local EAIOS 检查。RG 消费其有来源的结果和必要的
  共享状态；跨参与者结果验证继续使用 RG 的验证机制。
- 查询与取消作用于原任务。取消受理和实际执行终止分别记录。任务状态未知时保留
  原资源义务，重新连接或重启后按原身份对账。
- 请求重传使用原身份与原参数。已越过发送边界的未知任务恢复时先查询，避免再次
  执行姿态切换等有副作用的操作。
- Local EAIOS 在委派范围内使用本机资源。需要额外参与者或共享资源时，把需求交回
  RG 协调。RG 保留跨参与者资源承诺权，本地系统保留即时拒绝和安全处置权。

## 已有基础与实现缺口

| 位置 | 已有基础 | 本次需要完成的工作 |
| --- | --- | --- |
| Mission 与 Capability Catalog | 已知 Operation 与参数校验，目标通过 ExecutionIntent 传递 | 定义有明确范围的委派语义及部署选择方式，覆盖指定实体与自动选参与者的差别 |
| Control / Runtime | 操作支持检查、资源 Commit、attempt 与恢复 | 复用现有流程验证委派任务的资源占用、身份关联、重复请求和未知结果 |
| Node Service | HTTP、dynamic gRPC unary/server-streaming、MCP 驱动，私有 workflow 与 journal | 用真实接口确定可直接配置的部分，仅为实证缺口增加通用机制 |
| Robonix 接入 | 实验候选已封装 Liaison 任务提交与原生事件接收 | 核实本机任务受理、任务级终态、查询和取消，完成正式绑定与状态映射 |
| 设备接入 | 既有声明式操作配置与设备扩展 conformance | 提供一个有明确执行能力的设备范例，验证它与 EAIOS 参与者使用相同的调度与恢复流程 |

`integrations/robonix-task` 已提供显式启用的本机任务入口、持久身份与原生结果映射。
同一绑定用于状态查询和站立目标，狗2沿用单个 Connector 组合入口。正常任务结果、
规划失败和旧结果对账已经实现。真实运动取消、跨本机系统重启查询和多机验收继续推进。

目录示例采用现有 Catalog v0.3 格式，以部署局部 `task.delegate@v1` 声明本机任务范围，
profile 属性与参数在本机进行一致性检查。当前它表示人工监督的目标委派，逐技能强制
权限属于 Robonix。既有 Node 协议和 Runtime 生命周期承载该任务。

首个拒绝请求暴露了本机维护需求。`core/node-service/examples/reconcile_rejected_dispatch.rs`
通过现有独占 journal writer 和递增序列 API，将有独立未派发证据的原 handle-less
拒绝记录归约为 Failed。操作者必须提供精确原身份、digest、序列、拒绝原因和证据。
HTTP 400/404 本身不能证明无副作用，工具只接受操作者已经建立的本地证据，原始输入
和拒绝原因留在 journal。通用在线流程继续保留未知结果，工具不派发任何任务。

## 实施与验收顺序

1. 从实际 Robonix 客户端和服务端核对任务协议，固定受理、查询、终态与取消的语义，
   明确哪些字段是本机已有事实，哪些需要本机接口扩展。
2. 实现最小委派合同、Node 绑定和状态转换。保留已有完整能力操作，两类接入均经过
   正常任务入口。公共合同变更按对应版本规则处理。
3. 用隔离的软件参与者验证完整目标传递、范围拒绝、重复请求、结果归属、响应丢失、
   重启对账和取消，覆盖实际 Controller 与 Node 的正常入口。
4. 在狗2上执行用户授权的单次站立任务。保留 RG 提交、Commit、Bind、attempt、本机
   任务身份与 Robonix 结果，并记录现场观察。原语步骤由 Robonix 执行。
5. 验证同一入口的后续受支持目标，以及两个参与者的依赖协作、资源冲突与故障恢复。
   将单机接入结果和多机协调结果分别记录，形成 RG 的可重复回归用例。

功能、协议和验证代码在 RoboGuide 专题分支维护。原始真机日志、部署凭据与运行数据
按实验记录管理。推送与合并以实际差异、适用检查和人工审阅为依据。
