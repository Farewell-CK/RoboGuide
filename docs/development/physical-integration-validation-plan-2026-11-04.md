# RoboGuide 真机接入验证计划

日期为 2026-11-04。本文是接续狗2站立验收的执行计划，阶段与轮数为建议值。
执行前记录现场条件、版本、预算与参与者，按实际可用设备逐阶段推进。

本轮已开始执行，阶段实测结果见
[P0–P3 验收记录](acceptance/2026-11-04-dog2-p0-p3-validation.md)。
P2 已发现本机任务终态与全局安全停止证据之间的接入缺口。随后另经用户明确授权和
现场监护，完成了[单次公司门口导航到达](acceptance/2026-11-05-dog2-company-entrance-navigation.md)；
这只验证 P3 的到达子用例，不表示 P2、完整 P3 或自动恢复通过。
2026-11-05 的[后续现场验收](acceptance/2026-11-05-dog2-cancellation-field-validation.md)
已完成无副作用取消、旧任务正式结案和服务重启保持。运动终止证据及 P3 继续待验收。

## 起点与阶段目标

现有证据为狗2的一次站立闭环。固定 MissionPlan 经 Controller、正式 Node Protocol、
本机 Connector、Robonix Liaison/Pilot 与 Executor 完成，原生状态由 down 变为 standing，
RG Mission 和 attempt 均为 Completed。

当前仍需验证运动取消、原生系统重启后的任务查询、实体选择、多个参与者协调和
自然语言 Mission Request。`local-task-v1` 当前声明人工监督的委派范围，逐任务技能
权限隔离仍需在 Robonix 完善。之前出现过模型过载与迟到结果，回归应覆盖这些事实。

本轮阶段目标是形成一个可重复执行的多机闭环。RG 能选择正确的参与者、协调资源、
传递任务与结果，并在故障后保留已完成工作和未确认的资源义务。具身操作系统与
设备两类接入各提供真实参与者，公共调度和恢复机制接受统一验证。

依据见 [站立验收记录](acceptance/2026-11-04-robonix-task-delegation.md)、
[两类接入 ADR](../decisions/0231-local-eaios-and-device-integration.md)和
[项目目标](../project-goals-and-mvp.md)。

## 职责与证据

RG 负责目标、参与者、共享资源、任务依赖、执行身份和恢复。
Robonix 负责本机准入、任务分解、地图与地点解析、导航、动作执行、即时安全及本机结果。
设备适配层提供它实际实现的操作和可归属的执行状态。现场人员确认空间条件并观察
物理结果。各层结果按来源记录。

每次试验保存 Mission、attempt、Node/实体/LocalSystem 身份、本机 session/task/plan
关联、源码与配置摘要、原始回执、最终状态、资源占用和释放，以及现场观察。
记录所有提交，失败、拒绝、超时和人工介入保留在同一轮次清单。

## P0 固定部署基线与设备身份

在机器狗静止、没有活动任务时进行。

- 保存 Controller、Node、Connector 和 Robonix 的实际版本、启动参数与部署摘要。
- 对照真实设备建立狗1/狗2的实体与 Node 对应关系，分别维护凭据、状态目录和本机
  任务 journal。狗1首次接入先验证身份与只读状态。
- 验证正常启动、Node 重启、Connector 重启和一次完整上电启动的注册顺序。
- 验证 Controller 可达性、本机系统健康、能力就绪和状态新鲜度各自反映真实情况。

通过条件为设备身份唯一、状态来源正确、启动后能自动注册、历史任务可以查询。
恢复时间、状态过期时间和人工步骤实测记录，与部署配置中的期望窗口比较。

本阶段需要两台 Thor 可访问。狗1的运动控制与底盘上电安排在其物理试验前确认。
完整上电试验由现场人员操作设备电源。

## P1 单狗委派语义与资源占用

继续使用固定 MissionPlan，全部经 RG 正常任务入口。

| 用例 | 观察与通过条件 |
| --- | --- |
| 查询姿态和电量 | RG 收到有原任务归属的完成结果，记录值及新鲜度，现场姿态相符 |
| 已站立时要求站立 | Robonix 按当前状态完成目标，原生记录能说明是否实际调用动作 |
| 趴下后站立 | 两项独立目标使用同一委派入口，结果及前后依赖明确，现场分别确认 |
| 重传同一 attempt | 本机返回原 handle 和原结果，原生任务接纳次数保持一次 |
| 同一身份但改变参数 | 明确拒绝冲突输入，保留原任务 |
| 同狗两个竞争任务 | 用无位移任务先验证独占任务槽，等待或拒绝原因可查，终态后正常释放 |
| 本机拒绝任务或模型失败 | 区分本机拒绝、规划失败和通信不确定，证据充分时结束，缺证据时保留待对账 |

建议做 5 次只读任务和 3 组低频姿态试验。重复提交及并发首先使用无位移任务。
姿态试验逐项由现场确认，动作间以实际稳定状态作为进入下一项的依据。

## P2 取消、超时与重启对账

这一阶段同时包含实现补齐和真机协议验收。先用软件参与者覆盖故障，再对静止狗的
只读或明确可终止的本机任务做同样验证。

| 故障位置 | 需要验证的行为 |
| --- | --- |
| RG 接纳后、本机派发前取消 | 有确定未执行依据，原任务可结束并释放资源 |
| 本机任务运行时取消 | 原 session/task 的取消回执与任务终止证据关联，RG 据此收尾 |
| 本机已受理但回复丢失 | 重连按原身份查询，保留原 attempt 和预算 |
| Controller、Node 或 Connector 分别重启 | 已完成任务保持终态，未决任务按原身份恢复或进入待对账 |
| Robonix 重启 | 核对本机历史查询能力，未知历史具有明确状态与人工对账路径 |
| RG 链路暂时中断 | 本机按约定的失联策略处置，RG 状态按新鲜度变化，恢复后核对原任务 |
| deadline 到期与迟到结果 | 保留原 deadline，区分本机晚到结果与 RG 任务是否按时满足 |
| 模型服务过载或异常输出 | 原因可定位到模型依赖，已结束的规划失败完成资源清理 |

每类建议做 3 次，记录原始失败和恢复耗时。完成标准包括原生派发身份唯一、取消
作用域正确、未知结果持续保留、恢复后资源占用与真实任务一致。

运动任务进入下一阶段前，需要核实 Robonix 的任务终止、即时停止和失联策略。
当前“取消已受理”的回执不足以单独结束运动任务。若现有接口缺少最终证据，就在
Robonix 补齐并通过 Node 现有状态通道上报。网络故障注入最初限定在 RG 的通信链路。

## P3 单狗导航与复合任务

由现场选择视线内、短距离、可确认的路径。现有 Scene 中的“公司门口”作为候选目标，
执行前由 Robonix 核对当前地图、Scene 标注归属、定位及目标可达性。若路径较长，
先选择现场确认的较近目标。测试计划记录实际限速和本机到达判据。

1. RG 委派“到指定地点”，由 Robonix 完成本机起身、定位与导航。
2. 在受控短路径上通过 RG 请求取消，确认原导航任务结束及现场停止，再检查 RG 释放。
3. RG 委派“到指定地点并拍照”，检查本机任务结果、图片时间戳和产物引用。
4. 使用明确不存在的地点、地图不匹配或受控不可达条件，验证失败原因和资源收尾。

通过条件为到达或失败结果符合已记录的本机判据，原 Mission 与产物关联正确，取消
能完成任务级与物理级收尾。建议正常到达 3 次、运动取消 3 次，异常场景先在无位移
准入阶段验证。步态、轨迹、关节阈值由 Robonix 维护。

用户对站立的授权对应已完成试验。新的导航、趴下和运动取消场景应在现场具体目标、
路径与观察安排确定后进入执行。

## P4 两狗协作与全局资源协调

狗1通过 P0、P1，两个本机系统的任务生命周期均满足 P2 后开展。

| 用例 | RG 的验收重点 |
| --- | --- |
| 指定狗1或狗2执行相同只读目标 | 通过实体/Actor 绑定选择指定设备，跟踪完整绑定来源 |
| 自动选择一个可用参与者 | 基于所需能力、当前就绪、资源占用和明确策略选取；只有统一入口声明时继续要求任务适配依据 |
| 两狗执行相互独立的任务 | 执行身份、进度、结果与资源互相独立，可并行完成 |
| 带依赖的协作任务 | 例如狗1到A点采图，产物就绪后狗2执行已约定复核任务，后继依赖有明确证据 |
| 共享通道或区域 | 先用逻辑资源验证互斥，再在现场标定通道试验全局排程与本机避障配合 |
| 一狗在派发前掉线 | RG 重算候选或保持等待，选择与拒绝原因可查 |
| 一狗执行后结果不确定 | 保留原任务与占用，按确定的停止/恢复证据决定接替，已完成参与者的工作保留 |

自动恢复先验证无物理副作用的任务。移动任务的替代执行须同时满足原任务处置、
新参与者能力、当前地点与资源检查。建议正常协作 3 轮、资源竞争 3 轮、受控故障
各 3 轮，优先验证正常 Controller/Node 入口能够产生完整事件链。

## P5 具身操作系统与设备混合接入

首个混合实验建议使用已有 ThinkPad 或空闲 Orin 提供图像质量检测或推理服务。
它通过通用 RG Node 和轻量执行模块声明实际计算能力，直接消费真实图像产物。
若有独立空闲相机，再增加一个使用相机 SDK 的设备节点。

示例 Mission 为“狗2到目标点采图，计算节点处理该图片并返回结果”。这会验证一个
Robonix 参与者与一个普通计算参与者的能力匹配、任务依赖、Artifact 传递与错误归属。
图片以原摘要和版本定位，处理结果保存对应输入身份。

通过条件为两类参与者走相同的调度、Commit、Bind、结果和恢复流程，输入输出可
对应，缺能力或处理节点失败具有明确结果。建议正常流程 3 次，处理失败和产物暂时
不可用各 3 次。机械臂到货后可作为后续更复杂的设备接入验收对象。

## P6 自然语言入口与连续回归

在固定计划验证稳定后，启用包含委派操作与已实现能力的 MI 部署目录。

- 从正常 Mission Request 输入“让狗2站起来”“安排一只可用机器狗到指定点拍照”及
  一个已验证的协作请求，检查计划、Review、目标实体与最终执行的一致性。
- 验证无法澄清的地点、当前没有可用参与者和缺能力三类情况，记录请求状态、候选
  与规划判断的对应关系。
- 验证多轮修改只作用于原任务或明确的新任务，范围变化经过相应的计划与执行处理。
- 将前述已通过用例组成固定回归集。每次 RG、Connector 或 Robonix 更新后保存新版本
  的结果，再决定是否更新部署基线。

建议先冻结 10 条请求，包含单机、协作、缺信息与失败场景，逐条人工核对。
硬件动作范围只采用已获现场授权并通过前述验证的场景。

## 记录的指标与验收节奏

每轮记录任务结果、提交次数、原生受理次数、人工介入次数、错设备执行、重复动作、
未释放资源，以及队列、RG 派发、本机规划、实际执行和结果回传各段延迟。
取消单独记录请求接纳时间与本机实际终止时间。重启与断链记录检测和对账耗时。

错设备执行、重复有副作用的动作、无依据的成功和未终止任务的资源提前释放，作为
该轮必须修复的缺陷。性能目标根据已冻结预算和前几轮分段测量制定，最终报告同时
呈现总体成功率与失败归因。3 或 5 次的小样本用于工程回归，长期稳定性另设持续运行试验。

建议执行顺序为 P0/P1、P2、P3，随后 P4 与 P5，最后 P6。软件故障测试与设备接入准备
可在等待现场条件时推进。眼前下一批工作是固定部署版本、跑通只读任务结果查询、
核实取消终态与重启查回，再安排下一项现场姿态试验。
