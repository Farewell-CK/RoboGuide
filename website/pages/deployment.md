# 后端与网络

## 两类服务

| 服务 | 负责什么 | 相关源码 |
| --- | --- | --- |
| 视觉后端 | DINOv2 特征提取、障碍接口转发 | services/navi_vision/ |
| 室内障碍推理 | 室内语义分割与类别策略，由视觉入口转发 | services/navi_obstacle/ |
| Supabase 项目 | 账号认证、地图、路线、图片及访问控制 | navi_indoor/ 及项目配置 |

GPU 服务器上的数据库代理，只转发请求，不意味着 Supabase 数据库本体迁到了 GPU 服务器。
手机上的两项地址分别指向视觉入口和数据库入口；实际部署位置应以维护者的当前配置为准。

## 网络方式

- 同一局域网：手机可访问对应局域网地址，实际速度还取决于网络和服务负载。
- Tailscale：不同网络的设备通过私网互访，可能使用直连，也可能通过中继。
- 公网入口：由公网服务提供经过配置的访问入口，需要单独部署和验证。
- SSH 转发：依赖具体的隧道与设备配置，连接断开时转发入口也会受影响。

文档网站与 NAVI API 是不同服务。文档网站能打开，不代表视觉或数据库已经连通；
新增文档站也不会自动完成 NAVI API 的公网部署。

## 按顺序排查

1. 用手机确认所填写的入口可达，并检查视觉服务的 /health。
2. 检查登录和地图管理，区分数据库链路与视觉链路。
3. 查看导航诊断中的请求耗时、匹配分数和当前确认状态。
4. 比较 Wi-Fi 与移动流量的表现，结合 Tailscale 状态判断是否存在中继延迟。
5. 最后核对服务端处理耗时、GPU 负载和错误日志。

登录、图片下载、特征请求耗时应分开记录，不能把全部等待都归为 GPU 推理慢。
